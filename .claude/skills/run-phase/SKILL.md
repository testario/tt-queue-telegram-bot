## Задача

Ты — реализатор плана разработки Telegram Mini App. Выполни следующий алгоритм строго по шагам.

---

## Шаг 1: Определить текущую фазу

Прочитай файлы `plan/phase-*.md` в порядке номеров (1, 2, 3...).

Если передан аргумент `$ARGUMENTS` (номер фазы) — работай с этой конкретной фазой.
Иначе — найди **первую фазу**, в которой есть хотя бы один **невыполненный критерий**:
строка вида `- [ ]` (незакрытый чекбокс).

Фаза считается **завершённой**, если все критерии готовности (`- [ ]`) заменены на `- [x]`.
Фаза считается **невыполненной**, если есть хотя бы одна строка `- [ ]`.

Если все фазы выполнены — сообщи об этом пользователю и заверши работу.

---

## Шаг 2: Прочитать план фазы целиком

Прочитай соответствующий файл `plan/phase-N-*.md` **полностью**.
Также прочитай `plan/README.md` для понимания общей архитектуры.

Изучи уже существующий код в проекте, чтобы не дублировать и не конфликтовать:
- `src/` — существующий бот
- `mini-app/` — фронтенд (может не существовать на ранних фазах)

---

## Шаг 3: Подготовить директорию документации

Проверь существование `mini-app/docs/`. Если её нет — создай.

Создай (или открой, если уже существует) файл `mini-app/docs/phase-N.md`, где N — номер текущей фазы.
Этот файл будет журналом выполнения.

Запиши в начало файла:
```markdown
# Фаза N: <название фазы>

**Статус:** В работе
**Начато:** <дата>

## Журнал выполнения
```

---

## Шаг 4: Реализовать фазу пошагово

Выполняй каждый пункт плана последовательно. **После каждого выполненного подпункта**:

1. Запиши в `mini-app/docs/phase-N.md` раздел:
```markdown
### <N.X> <название подпункта>

**Что сделано:** <краткое описание — 1-3 предложения>
**Файлы:** `путь/к/файлу1`, `путь/к/файлу2`
**Решения:** <если было нетривиальное решение — объясни почему>
```

2. Переходи к следующему подпункту.

Реализуй код **точно по плану** — без добавления лишних абстракций, без рефакторинга
того, что не упомянуто в плане, без опережающей реализации следующих фаз.

---

## Шаг 5: Проверить критерии готовности

После реализации всего кода фазы пройдись по разделу **"Критерии готовности"** в файле плана.

Для каждого критерия:
- Если реализован — замени `- [ ]` на `- [x]` в файле плана
- Если **не реализован** (не хватает информации, зависит от внешней системы, невозможно проверить без запуска) — оставь `- [ ]` и **задокументируй причину** в `mini-app/docs/phase-N.md`

---

## Шаг 6: Завершить журнал

Обнови `mini-app/docs/phase-N.md`, добавив в конец:
```markdown
## Итог

**Статус:** Завершена / Частично завершена
**Выполнено критериев:** X из Y
**Невыполненные критерии:** <перечисли, если есть>
**Следующая фаза:** phase-M
```

## Жёсткие ограничения — ОБЯЗАТЕЛЬНО СОБЛЮДАТЬ

### Git — только чтение истории

**ЗАПРЕЩЕНО:**
- `git commit`
- `git add`
- `git push`
- `git reset`
- `git checkout` (переключение веток или восстановление файлов)
- `git merge`, `git rebase`, `git stash`
- Любая команда git, изменяющая состояние репозитория или индекса

**РАЗРЕШЕНО:**
- `git log` — просмотр истории
- `git show` — просмотр содержимого коммита
- `git diff` — сравнение (без применения)
- `git status` — просмотр статуса
- `git blame` — история строки

Если понадобится зафиксировать изменения — сообщи пользователю: "Готово к коммиту. Зафиксируй изменения самостоятельно."

### Не трогать существующий код бота

**ЗАПРЕЩЕНО** изменять файлы в `src/` кроме случаев, явно описанных в плане текущей фазы
(например, Фаза 1 добавляет `src/interfaces/webapp/`).

### Не забегать вперёд

Реализуй только текущую фазу. Не создавай файлы и структуры, которые относятся к следующим фазам.

### Документировать каждый шаг

Каждый подпункт плана должен быть задокументирован в `mini-app/docs/phase-N.md` **сразу после выполнения**.
Не откладывай документацию на конец.
